# Codex fork: agent and voice-release workflow

This repository is an upstream Codex fork. Its **portable macOS Codex Voice** distribution is maintained separately from upstream Codex's standard CLI.

## Scope and source of truth

- For changes to realtime voice, local speech, voice packaging, or the portable Voice release, use the current `feat/portable-codex-voice-release` branch as the integration base. Check its current remote HEAD before editing or building. Do not assume `main` already includes the Voice implementation.
- Do feature work in a separate linked worktree at `<permanent-checkout>.worktrees/<branch-slug>`. Never overwrite another worktree's dirty changes. Keep the permanent checkout on its remote default branch.
- These instructions augment the user's global `~/.codex/AGENTS.md`; never modify its generated copy directly.
- Release source of truth: [portable Voice workflow](.github/workflows/portable-codex-voice.yml). Release consumer: `ArthurZakirov/dotfiles`, file `home/.chezmoidata.toml`, section `[codexVoice]`. Discover its actual location instead of assuming a particular home directory.

## Voice behavior to preserve

- When launched with dedicated `codex-voice` and local verbatim speech enabled, speak **every completed, visible assistant message**: commentary/progress and final answers, whether the user spoke or typed, **even before a microphone call is started**. The regular `codex` launcher remains silent unless explicitly opted in. Do not speak private reasoning, tool logs, or replayed historical messages.
- Local speech uses one ordered queue. New typed input or microphone transcription must not discard a previously queued message. Detect the language from the visible assistant answer and select a matching local macOS voice for German or English; leave unsupported/ambiguous text on the system default. Do not transmit text to a paid/external classification API.
- On macOS, **Space pauses/resumes the currently speaking local synthesizer**, without losing its position, canceling the Voice session, or dropping queued messages. Preserve normal Space input when the composer contains text, no local speech is active, or a dialog/transcript interaction owns the key. Ignore key-repeat toggles.
- The separate `codex-voice` launcher should enable `CODEX_REALTIME_VERBATIM_SPEECH=1` by default; avoid modifying the stock `codex` command.
- Preserve the release's independent normal `codex`, existing voice experiments, and voice helper/native-runtime verification.

## Voice change: required end-to-end completion

For each user-requested Voice feature or fix, do not call work complete merely because a PR was merged. Carry the work through these gates, unless the user explicitly requests code-only changes or a gate is blocked. Report each gate's actual result.

1. **Mandatory local-first pre-release gate.** On the Apple Silicon Mac, check the actual installed release receipt, sound output/mute state and installed `say -v '?'` voices. Change code in a separate feature worktree. Before triggering any heavy GitHub CI/release, run Rustfmt, focused unit tests, native macOS speech process tests, and a targeted local debug build. Use the repository's pinned Rust toolchain and an existing Cargo build cache where possible; check disk capacity first and avoid a second full build directory. If Cargo is installed but absent from `PATH`, locate the toolchain rather than silently skipping tests. No release build is an acceptable substitute for local functional validation.
2. **Prove the audible user workflow locally before packaging.** Launch the freshly built local debug CLI with `CODEX_REALTIME_VERBATIM_SPEECH=1`, **not** an older installed `codex-voice` release. Type English and German prompts and verify the correct language voice, FIFO order and Space pause/resume; for microphone changes, test a live voice session. Confirm the correct audio output device is not muted. If the agent cannot personally hear the result, request an explicit listening confirmation before an expensive release; mark the audio gate *unverified* until then. Documentation-only edits do not require a live speech test.
3. **Review and merge.** Create a focused PR into `feat/portable-codex-voice-release`; review actionable comments; monitor CI; repair failures without disabling the check that detects them. Merge only after the appropriate tests and review gates pass, respecting the user's explicit merge instructions.
4. **Produce a new immutable release only when requested and after the local validation gate passes.** Normal feature PR merges **must not** launch expensive release builds. After the user requests a release, update the dedicated `.github/voice-release-request` file in a focused PR against `feat/portable-codex-voice-release`. Only a push changing that file on the release branch triggers [the release workflow](.github/workflows/portable-codex-voice.yml). Optionally use `workflow_dispatch` where GitHub allows it. Monitor the run and repair build/package failures. Never reuse or overwrite an existing `voice-v<version>-r<n>` tag. For the two Apple Silicon Macs, verify the release has **one `aarch64-apple-darwin` archive** and `SHA256SUMS`; do not request or publish Intel artifacts.
5. **Verify before promotion.** Ensure the published release points to the intended merged commit, artifacts and checksums match, native voice-helper signing/build provenance are valid, and the package runs in a disposable HOME. Check `codex-voice --version` and `codex-voice --no-daemon --help`; verify the voice behaviors interactively when possible. A missing or failing artifact is a release blocker, not a reason to change the Dotfiles tag.
6. **Promote to Dotfiles.** Only after a release is verified, update `[codexVoice].tag` in `ArthurZakirov/dotfiles/home/.chezmoidata.toml` in a **fresh Dotfiles feature worktree**. Keep `enabled = true`. Run the existing real-Chezmoi integration/system tests with an isolated HOME. Commit, push, open a Dotfiles PR, resolve review and CI failures, and merge only with the user's authorization and required gates. Never apply an unmerged Dotfiles feature worktree to a real HOME.
7. **Verify onboarding.** After Dotfiles promotion, `chezmoi update` should install or verify the matching release without unnecessary reinstallation; `codex-voice --no-daemon` should run on both Macs. If the other Mac is disconnected, report that its real installation remains unverified.

### Automation and permissions

- `AGENTS.md` is a **task policy for agents, not an event handler**. It cannot wake an agent after a merge or run a GitHub workflow by itself. GitHub Actions handles the build on a release-branch push; a connected agent performs the verified cross-repository Dotfiles promotion. For fully unattended promotion, configure a separately authorized cross-repository GitHub App/credential and a guarded event workflow. Do not assume `GITHUB_TOKEN` in Codex can write to Dotfiles.
- **Cost constraint:** never choose GitHub-hosted *larger* runners, private-repository billable runs, paid services, or modify billing/payment settings. Prefer standard hosted runners in public repositories, which GitHub documents as free; verify repository visibility and runner class before launching. Use only the default free GitHub cache allowance (10 GiB) and never raise its quota. Never build Intel packages for the two M4 Macs or run full upstream matrices. A single arm64 package still needs significant compilation time; do not promise instant releases.
- Use the authenticated GitHub/SSH identity already available, never print access tokens, never create or inspect billing methods, and never bypass failed release validation.
- If any step is blocked by credentials, absent runner capacity, failed checks, or interactive audio verification, complete what is safe, report the exact blocker and remaining step, and **never silently claim the latest code is already shipped**.
